The pattern `_OBSOLETE_FOLD_RE` is written as `(?:(?<![ \t])[ \t]+)?\r\n[ \t]+`, and it helps to read it in three pieces from left to right. First comes an optional group for the whitespace before the line break (OWS): one or more spaces or tabs, guarded by a lookbehind that says the character just before them must not itself be a space or tab. Then comes the required CRLF, the actual line break. Then comes the required whitespace after it (RWS): one or more spaces or tabs starting the continuation line. The leading group exists so that whitespace before the CRLF is swallowed into the replacement instead of surviving it — without it, a value like `"before \t\r\n\t after"` would unfold to `"before \t after"`, keeping a stray tab. [[diff:src-urllib3-connection.py:80-82]] [[diff:test-test_connection.py:218]]

The lookbehind is there for speed, not just correctness. Without it, a pattern like `(?:[ \t]+)?\r\n` would be quadratic on an input such as `"a"` followed by a long run of spaces, then `"b"`, with a CRLF somewhere in the value. The regex engine tries a match at every offset; at each of the many offsets inside the space run, the greedy `[ \t]+` first consumes the rest of the run and then gives characters back one at a time looking for the CRLF, redoing the same work over and over. The lookbehind `(?<![ \t])` stops that: it pins the optional whitespace group to the single position right after a non-space, so each offset is tried once instead of once per remaining space. [[diff:src-urllib3-connection.py:80-82]]

A simpler design would skip the OWS handling in the regex entirely and clean up whitespace separately — for example, split the value on `\r\n` and then strip each piece. That would also run in linear time with no regex tricks at all. The author's choice keeps the whole rule in one substitution instead: one pattern, one replacement, no second pass. The reason is inferred, since the change never states it, but the trade is visible — a single `_normalize_header_value` call does everything, at the cost of a pattern readers must decode piece by piece. [[diff:src-urllib3-connection.py:85-88]]

The lookbehind inspects the original string, not the output of earlier matches, which matters when folds sit next to each other. Take the value `"one\r\n \r\n\tthree"`: the first match is `"\r\n "` and its greedy trailing `[ \t]+` consumes the space. At the second `\r\n`, the character before is that already-consumed space, so the lookbehind blocks the optional OWS group and the match starts cleanly at the CRLF. Step by step, the engine never re-reads what the previous match already ate, which is exactly the linear behaviour the pattern promises. One claim stays untested: no test exercises the linear-time behaviour. The existing cases are all short, so if the pattern ever regressed to a quadratic one, the suite would still pass. Likewise a bare `\r\n` not followed by a space or tab never matches, because the trailing `[ \t]+` is required — and that rejection path is untested too. The gap matters because a performance regression here would show up only on adversarially long headers in production, never in the test suite. [[diff:src-urllib3-connection.py:82]]
