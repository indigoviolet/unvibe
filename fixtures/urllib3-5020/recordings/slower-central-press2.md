Start with what the server sends: an `obs-fold`, meaning an old server puts one header value on two lines, with the second line starting after a line break (CRLF) and some whitespace. Concretely, the bytes on the wire look like `Set-Cookie: a=1`, then CRLF, then a space, then `path=/` — one cookie, split in two. The change puts the value back together right after parsing, while the response is still fresh and before anything else reads the headers, because waiting would let each consumer trip over the raw split on its own. Finding each split is the job of the regex `_OBSOLETE_FOLD_RE`, which reads left to right: any spaces or tabs first, then the CRLF that ends the line, then the required whitespace that marks the next line as a continuation rather than a new header. Wherever it matches, `_normalize_header_value` writes a single space, so the two halves become the single value `a=1 path=/`. [[diff:src-urllib3-connection.py:80-88]]

Now follow one header through `_normalize_header_values`, which runs this unfolding over every header on Python's `HTTPMessage`, one at a time and in arrival order. Take the folded `Set-Cookie` above: the function compares the unfolded value with the original, sees that it changed, removes the old headers from the message object, and adds the cleaned `Set-Cookie: a=1 path=/` back exactly where it was, keeping the original order of every header. Deleting and re-adding matters because the message object is the shared record both sides read — patching it in place keeps `HTTPMessage` and urllib3's `HTTPHeaderDict` in agreement, instead of one holding the raw fold and the other the cleaned value. The cleaned headers come back as the function's result, and `getresponse` builds the `HTTPHeaderDict` from them, which is why downstream cookie code such as Requests now receives one clean value per header.
