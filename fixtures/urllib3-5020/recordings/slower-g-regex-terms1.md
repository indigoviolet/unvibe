`_OBSOLETE_FOLD_RE` is the regular expression that recognizes one fold: `(?:(?<![ \t])[ \t]+)?\r\n[ \t]+`. OWS means "optional whitespace" — the spaces or tabs that may sit before the line break — and RWS means "required whitespace", the spaces or tabs that must start the continuation line. Reading left to right: an optional OWS group, then the required CRLF, then the required RWS. The leading group exists so whitespace before the CRLF is swallowed into the replacement: without it, `"before \t\r\n\t after"` would unfold to `"before \t after"`, keeping a stray tab. [[diff:src-urllib3-connection.py:80-82]] [[diff:test-test_connection.py:218]]

The lookbehind `(?<![ \t])` is there for speed, not just correctness. A lookbehind is a zero-width check on the character just before the current position — it asserts something without consuming it. Without it, a pattern like `(?:[ \t]+)?\r\n` would be quadratic on a value with a long space run plus a CRLF elsewhere: at each of the many offsets inside the run, the greedy `[ \t]+` would consume the rest of the run and give characters back one at a time looking for the CRLF. The lookbehind pins the optional group to the single position right after a non-space, so each offset costs one check instead of one scan. [[diff:src-urllib3-connection.py:80-82]]

The alternative is to not require the OWS in the regex and strip trailing whitespace separately — for example, split on `\r\n` and then strip each piece. That is linear with no regex tricks. The author's choice keeps the whole rule in one substitution call instead; the reason is inferred, but the trade is visible: callers need a single `_normalize_header_value` with no second pass, at the cost of a pattern readers must decode piece by piece. The helper also skips values with no `\r\n` at all, so ordinary headers never reach the regex. [[diff:src-urllib3-connection.py:85-88]]

The lookbehind inspects the original string, not the output of earlier matches. Take `"one\r\n \r\n\tthree"`: the first match is `"\r\n "` and its greedy trailing `[ \t]+` consumes the space. At the second `\r\n`, the character before is that already-consumed space, so the lookbehind blocks the optional group and the match starts cleanly at the CRLF. Step by step, the engine never re-reads what the previous match already ate — exactly the linear behaviour the pattern promises. One claim stays untested: no test exercises the linear-time behaviour. The existing cases are all short, so a regression to a quadratic pattern would still pass. A bare `\r\n` not followed by a space or tab never matches either, because the trailing `[ \t]+` is required — and that rejection path is untested too. [[diff:src-urllib3-connection.py:82]]
