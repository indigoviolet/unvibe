The fix has to reach two copies of the headers, and "copy" here means two live views of the same response: urllib3's `HTTPHeaderDict` and the standard library's `HTTPMessage`. `getresponse` used to build the `HTTPHeaderDict` from `httplib_response.msg.items()`, while the `HTTPMessage` itself stayed on the response as `_original_response.msg`. The description says cookie consumers such as Requests read that message, not urllib3's dict — so a fix that cleaned only the `HTTPHeaderDict` would leave the raw CRLF in `msg`, and Requests could re-emit it. That is why `_normalize_header_values` also writes the cleaned values back into the message. [[diff:src-urllib3-connection.py:647-651]] [[desc:d-p2]] [[diff:src-urllib3-connection.py:102-108]] [[diff:test-with_dummyserver-test_socketlevel.py:124-146]]

The write-back is a delete and re-add of every header, on the same `HTTPMessage` object — identity here means the object in memory stays the same object, only its contents change. The alternative is to build a fresh `HTTPMessage` and swap it onto the response, which would change object identity: anything holding the old reference would keep seeing folded values. The socket test asserts `_original_response.headers is _original_response.msg`, and the unit test asserts that `defects` and `policy` are the same objects before and after. [[diff:test-with_dummyserver-test_socketlevel.py:141]] [[diff:test-test_connection.py:248-249]] [[diff:src-urllib3-connection.py:103-104]]

A third option is to fix the parse itself, by patching `http.client.parse_headers` or subclassing the response class, so values would arrive unfolded before any copy exists. That would mean patching a standard-library module-level function, affecting every user of `http.client` in the process — a blast radius far beyond urllib3. No code in this change tries it. Normalizing after `begin()` inside `getresponse` keeps the change local to urllib3's own connection class.

The costs are these. urllib3 now rewrites an object it does not own, and it depends on `HTTPMessage` semantics: `del message[name]` drops every occurrence of a name, and `message[name] = value` appends, so the loop works only because it deletes everything first and then re-adds in order. Because the rewrite runs only when `headers_changed` is true, responses without folds never touch the message. The function also returns the cleaned items, so the `HTTPHeaderDict` is built from the same values the message now holds.
